# BOJ 32510 - 키가 비슷한 친구

## 문제 요약

- N명의 사람, 각각 키 `A[i]`
- 각 i에 대해: `j <= i`이고, `A[i]-K <= A[j] <= A[i]`인 j 중 **가장 작은 j**를 찾아 `(i - j)`를 합산

---

## 알고리즘 비교

### 접근법 1: 세그먼트 트리

- 키 값을 인덱스로, 원래 위치를 값으로 저장
- 왼→오 순회하며 `query` 후 `update` → `j <= i` 조건 자동 만족
- **시간복잡도**: O(N log MAX_H)

### 접근법 2: 모노토닉 덱 (최적)

- 오프라인 처리: 키별로 결과를 미리 계산
- 슬라이딩 윈도우 + 덱으로 범위 내 최소 인덱스 관리
- **시간복잡도**: O(N log N) (정렬) + O(N) (덱 처리)

---

### 3. 2차 최적화 (통과)

> **핵심: 함수 인라인화 + 지역 변수 사용**

#### (1) `main()` 함수로 감싸기

```python
# Before: 전역 변수

# After: 지역 변수

```

- Python에서 지역 변수 접근이 전역보다 **~20% 빠름**
- LEGB 규칙: Local > Enclosing > Global > Built-in

#### (2) `query()`, `update()` 함수 인라인화

```python
# Before: 함수 호출 400만 번
for i in range(N):
    min_idx = query(lo, h)   # 함수 호출
    update(h, i)              # 함수 호출

# After: 인라인
for i in range(N):
    # query 로직 직접 작성
    res = INF
    l = lo + MAX_H
    ...
    # update 로직 직접 작성
    p = h + MAX_H
    ...
```

- 함수 호출 오버헤드 제거 (N번 × 2 = 최대 400만 번 절약)
- **이것이 가장 큰 영향!**

#### (3) 비트 연산 사용

| Before | After |
|--------|-------|
| `//= 2` | `>>= 1` |
| `* 2` | `<< 1` |
| `* 2 + 1` | `<< 1 \| 1` |

#### (4) 내장 함수 호출 제거

```python
# Before
tree[h] = min(tree[h*2], tree[h*2+1])
lo = max(0, h - K)

# After
left = tree[h << 1]
right = tree[(h << 1) | 1]
tree[h] = left if left < right else right
lo = h - K if h >= K else 0
```

### 4. 3차 최적화: 모노토닉 덱 (최적해)

> **핵심: 같은 키를 가진 사람들은 같은 결과를 공유한다!**

#### 알고리즘 구조

```python
# 1단계: 각 키의 최소 인덱스 저장
mins = defaultdict(lambda: INF)
for i in range(N):
    mins[A[i]] = min(mins[A[i]], i)

# 2단계: 키를 오름차순 정렬하여 순회
q = deque()
for h in sorted(A):
    # 범위 벗어난 키 제거 (h - K 미만)
    while q and q[0] < h - K:
        q.popleft()

    # 덱 뒤에서 현재보다 인덱스 큰 것 제거
    while q and mins[q[-1]] > mins[h]:
        q.pop()

    q.append(h)
    results[h] = mins[q[0]]

# 3단계: 결과 합산
for i in range(N):
    ans += i - results[A[i]]
```

#### 모노토닉 덱의 동작

```
키를 오름차순 순회: [1, 2, 3, 5, 5, 6, ...]

덱 상태 (키 값 저장, 인덱스 기준 단조증가):
┌─────────────────────────────────────┐
│ front                         back  │
│ [가장 작은 인덱스] ... [현재 키]     │
└─────────────────────────────────────┘

- front: 범위 [h-K, h] 내에서 가장 작은 인덱스를 가진 키
- 키가 증가하면서 범위도 이동 (슬라이딩 윈도우)
```

#### 왜 뒤에서 제거해도 되는가?

```
상황: 덱에 키 X가 있고, 새로운 키 h가 들어올 때
     - h > X (키 오름차순 순회)
     - mins[X] > mins[h] (X의 인덱스가 h보다 큼)

X를 제거해도 되는 이유:
1. X는 이미 자기 결과(results[X])를 계산 완료
2. 이후 키 j가 X와 h를 모두 범위에 포함하면,
   h의 인덱스가 더 작으므로 X는 어차피 선택 안 됨

→ "인덱스가 더 큰 키는 앞으로 절대 최적해가 될 수 없다"
```

#### 시간복잡도 분석

| 연산 | 횟수 |
|------|------|
| 각 키는 덱에 **1번 삽입** | O(N) |
| 각 키는 덱에서 **1번 제거** | O(N) |
| 정렬 | O(N log N) |
| **총합** | **O(N log N)** |
