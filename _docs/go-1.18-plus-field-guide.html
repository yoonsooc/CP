Go 1.18 (2022.03) 부터 Go 1.27 (2026.08) 까지

Go 1.18+ 필드 가이드

제네릭 도입 이후 4년 반 동안 Go에 들어온 변화 가운데, 현업 코드에서 실제로 자주 마주치는 것만 골라 정리했습니다. 기능마다 무엇이 바뀌었는지, 어디에 쓰는지, 그리고 어떤 비판이 있는지를 함께 적었습니다.

기준일 2026-08-23 최신 안정 버전 Go 1.27 출처는 각 항목 하단에 링크

범위와 읽는 법

Go는 매년 2월과 8월에 새 버전을 내고, 최근 두 버전만 보안 패치를 받습니다. 그래서 2026년 8월 현재 공식 지원 범위는 1.26과 1.27이고, 현업 프로젝트의 go.mod에 적힌 버전은 대개 1.22에서 1.25 사이에 분포합니다. 이 문서는 "지금 1.22 근처에 있는 프로젝트를 1.27까지 끌어올린다면 무엇이 달라지는가"라는 관점으로 읽으면 가장 유용합니다.

각 항목에는 도입 우선순위를 표시했습니다.

지금 도입 새 코드에서 기본으로 써야 하는 것 권장 알면 코드가 짧아지거나 안전해지는 것 상황에 따라 특정 워크로드나 팀 규모에서만 이득 실험 GOEXPERIMENT 뒤에 있거나 아직 흔들리는 것

한 가지 전제. Go의 "Go 1 호환성 약속"은 컴파일이 계속 된다는 약속이지 동작이 그대로다는 약속이 아닙니다. 1.21부터 go.mod의 go 줄이 언어 의미와 런타임 기본값을 결정하는 스위치가 됐기 때문에, 이 줄을 올리는 순간 for 루프 의미(1.22), 타이머 채널 동작(1.23), ServeMux 리다이렉트 코드(1.26) 같은 것이 함께 바뀝니다. 문서 곳곳의 "이 줄을 올리면" 이라는 표현이 바로 이 뜻입니다.

1언어

Go는 언어 자체를 거의 바꾸지 않는 것으로 유명했습니다. 그 기조가 깨진 것이 1.18이고, 이후 네 번의 의미 있는 언어 변경이 있었습니다.

제네릭의 성숙

1.18 → 1.24 → 1.26 → 1.27 지금 도입

1.18에서 타입 매개변수가 들어왔지만, 처음 몇 년은 "함수와 타입에만 쓸 수 있고 메서드에는 못 쓴다"는 제약이 가장 큰 불만이었습니다. 이 빈틈이 단계적으로 메워졌습니다.

  • 1.24 제네릭 타입 별칭. type Set[T comparable] = map[T]struct{} 처럼 별칭에도 매개변수를 붙일 수 있습니다.
  • 1.26 자기참조 제약. type Adder[A Adder[A]] interface { Add(A) A } 같은 선언이 가능해져 "자기 타입을 받아 자기 타입을 돌려주는" 인터페이스를 표현할 수 있습니다.
  • 1.27 제네릭 메서드. 메서드가 자기만의 타입 매개변수를 가질 수 있습니다. 단, 인터페이스의 메서드는 여전히 타입 매개변수를 가질 수 없습니다.
// Go 1.27: 메서드에 타입 매개변수
type List[T any] struct{ items []T }

func (l *List[T]) Map[U any](f func(T) U) *List[U] {
    out := &List[U]{items: make([]U, 0, len(l.items))}
    for _, v := range l.items {
        out.items = append(out.items, f(v))
    }
    return out
}

// 1.27 이전에는 패키지 수준 함수로 우회해야 했다
func Map[T, U any](l *List[T], f func(T) U) *List[U] { /* ... */ }
현업에서

컬렉션 유틸리티(Map, Filter, 우선순위 큐), 리포지토리 계층의 공통 CRUD, 옵션 패턴, 타입 안전한 이벤트 버스에 자리잡았습니다. 반대로 "인터페이스로 충분한 곳"에 제네릭을 쓰면 오히려 읽기 어려워지므로, Go 팀이 낸 When To Use Generics의 기준(같은 코드를 타입만 바꿔 반복할 때, 그리고 메서드 없이 동작하는 자료구조일 때)이 여전히 유효합니다.

비판적 시각

성능이 항상 좋아지는 것은 아닙니다. Go 제네릭은 C++ 처럼 타입마다 코드를 찍어내지 않고 "GC shape" 단위로 묶은 뒤 사전(dictionary)을 넘기는 방식입니다. PlanetScale의 Vicent Martí는 1.18 시점에 이 방식 때문에 인터페이스 메서드를 호출하는 제네릭 함수가 인터페이스 버전보다 느려지는 사례를 벤치마크로 보였습니다. 이후 컴파일러 개선으로 격차는 줄었지만 구조는 같습니다. 핫 패스에서 제네릭으로 바꿀 때는 반드시 벤치마크를 같이 돌리는 것이 안전합니다.

5년 반이 걸렸습니다. 제네릭 메서드는 1.18 설계 당시 이미 요구됐지만 1.27에야 들어왔고, 인터페이스 메서드의 타입 매개변수는 여전히 없습니다. "단순함을 지킨다"는 원칙과 "필요한 표현력"이 충돌할 때 Go는 수년 단위로 느리게 움직인다는 점을 감안해 두는 것이 좋습니다.

for 루프 변수가 반복마다 새로 만들어진다

1.22 지금 도입

1.21까지는 for i, v := range xs의 i, v가 루프 전체에서 하나의 변수였습니다. 그래서 고루틴이나 클로저가 그 변수를 잡으면 마지막 값만 보는 버그가 생겼고, 그래서 v := v라는 관용구가 필요했습니다. 1.22부터는 go.mod의 go 줄이 1.22 이상인 모듈에서 반복마다 새 변수가 만들어집니다. 같은 버전에 for i := range 10 처럼 정수에 바로 range를 거는 문법도 들어왔습니다.

// go 1.22 이상 모듈에서는 v := v 가 필요 없다
for _, v := range items {
    go func() { process(v) }()   // 각 고루틴이 자기 v 를 본다
}

for i := range 10 { fmt.Println(i) }   // 0..9
현업에서

Uber가 자사 코드베이스의 데이터 레이스를 분류한 보고에서 루프 변수 캡처가 가장 흔한 패턴이었습니다. 그만큼 이 변경의 실효는 큽니다. 다만 이 변경은 go 줄을 올려야 적용되므로, 오래된 모듈을 올릴 때 v := v 제거는 go fix(1.26, 아래 참고)가 해 줍니다.

비판적 시각

이것은 명백한 의미 변경이고, "호환성 약속"을 go.mod 버전 게이트로 우회한 첫 사례입니다. Russ Cox는 구글 전체 코드에서 이 변경으로 깨지는 테스트가 극소수였고 그마저 기존 버그였다고 보고했지만, 이 선례 덕분에 이후 타이머 채널(1.23), 리다이렉트 코드(1.26) 같은 동작 변경도 같은 방식으로 들어오게 됐습니다. go 줄을 올리는 것을 "문법 버전 올리기"가 아니라 "런타임 동작 변경에 동의하기"로 인식해야 합니다.

참고

이터레이터 (range over func)

1.23 권장

특정 형태의 함수에 for range를 걸 수 있게 됐습니다. iter.Seq[V]는 func(yield func(V) bool), iter.Seq2[K, V]는 func(yield func(K, V) bool) 타입의 별칭입니다. 표준 라이브러리의 slices, maps, strings, bytes에 이터레이터를 주고받는 함수가 대거 추가됐습니다.

func (l *List[T]) All() iter.Seq2[int, T] {
    return func(yield func(int, T) bool) {
        for i, v := range l.items {
            if !yield(i, v) { return }   // 호출자가 break 하면 멈춘다
        }
    }
}

for i, v := range l.All() { /* ... */ }

keys := slices.Sorted(maps.Keys(m))         // 맵 키를 정렬된 슬라이스로
for line := range strings.Lines(text) { }   // 1.24, 줄 단위 순회(할당 없음)
현업에서

직접 이터레이터를 "만드는" 일보다 표준 라이브러리가 돌려주는 이터레이터를 "소비하는" 일이 훨씬 많습니다. maps.Keys가 슬라이스가 아니라 iter.Seq를 돌려준다는 점, 그래서 slices.Collect나 slices.Sorted로 감싸야 한다는 점만 알아도 대부분의 코드가 읽힙니다. DB 커서, 페이지네이션 API, 대용량 파일 스트리밍처럼 "전부 메모리에 올리고 싶지 않은" 자료를 노출할 때 직접 만들 가치가 있습니다.

비판적 시각

"단순한 언어"에 가장 어울리지 않는 기능이라는 평이 많습니다. "함수를 range 하면, 그 함수가 콜백을 호출하고, 콜백이 bool을 돌려줘서 중단을 알린다"는 구조는 처음 보는 사람이 바로 이해하기 어렵습니다. Miguel Young de la Sota의 글은 push 방식 설계의 한계와 컴파일러가 이를 되감는 복잡한 변환을 비판적으로 분석했고, Chris Siebenmann은 yield의 반환값을 무시하는 실수가 얼마나 쉬운지 지적했습니다. 또 iter.Pull은 내부적으로 코루틴을 쓰기 때문에 핫 루프에서는 비용이 눈에 띕니다. 팀 내 합의 없이 직접 이터레이터를 남발하면 코드 리뷰 비용이 크게 늘어납니다.

2표준 라이브러리

"외부 패키지를 하나 줄일 수 있는가"를 기준으로 골랐습니다. 정렬/탐색, 로깅, 라우팅, JSON이 그 네 축입니다.

slices, maps, cmp 와 내장 min / max / clear

1.21 → 1.23 지금 도입

제네릭 기반으로 만든 첫 표준 패키지들입니다. sort.Slice와 reflect 기반 비교가 필요 없어졌고, 1.23에서 이터레이터 버전(slices.All, slices.Values, maps.Keys, slices.Collect)이 추가됐습니다.

slices.Sort(a)
slices.SortFunc(users, func(x, y User) int { return cmp.Compare(x.Age, y.Age) })
i, ok := slices.BinarySearch(a, 42)
if slices.Contains(roles, "admin") { }
a = slices.Compact(a)               // 연속 중복 제거
best := max(x, y, z)                // 내장 함수
clear(m)                            // 맵 비우기
현업에서

golang.org/x/exp/slices를 쓰던 코드는 import 경로만 바꾸면 됩니다. sort.Slice는 인덱스 클로저를 받아 실수하기 쉬웠는데 slices.SortFunc는 값 둘을 받는 비교 함수라 실수가 줄었습니다. go fix(1.26)가 sort.Slice→slices.SortFunc, 수동 루프→slices.Contains 같은 치환을 자동으로 해 줍니다.

비판적 시각

표준이 생겼다고 해서 lo(samber/lo) 같은 유틸리티 패키지가 사라지지는 않았습니다. Map, Filter, Reduce는 여전히 표준에 없고, Go 팀은 "for 루프로 쓰라"는 입장을 유지합니다. 그래서 팀마다 "표준만 쓴다"와 "lo를 허용한다"가 갈리고, 이 합의를 먼저 하지 않으면 같은 저장소 안에 두 스타일이 섞입니다.

errors 와 작은 편의 기능 모음

1.20 → 1.27 권장
  • 1.20 errors.Join(errs...)와 fmt.Errorf("...: %w, %w", a, b). 여러 에러를 하나로 묶고, errors.Is/As가 트리 전체를 탐색합니다. 검증 에러 여러 개를 한 번에 돌려줄 때 씁니다.
  • 1.21 context.WithoutCancel(부모 취소를 끊고 값만 상속), context.AfterFunc, sync.OnceValue. 요청 컨텍스트에서 비동기 후처리를 분리할 때 WithoutCancel이 정석이 됐습니다.
  • 1.22 math/rand/v2. 자동 시드, rand.N(10) 같은 제네릭 함수, 더 빠른 ChaCha8/PCG 생성기. 1.27에서는 Rand.N이 제네릭 메서드의 첫 표준 사용 사례가 됐습니다.
  • 1.23 unique.Make. 문자열 인터닝을 표준으로 제공합니다. 같은 문자열이 수백만 개 반복되는 로그 파서나 라벨 저장소에서 메모리를 크게 줄입니다.
  • 1.25 sync.WaitGroup.Go(f). Add(1), go func(){ defer Done() ... }() 세 줄이 한 줄이 됩니다.
  • 1.26 errors.AsType[E](err). var e *MyErr; errors.As(err, &e)의 제네릭 버전으로, 포인터 변수를 따로 선언할 필요가 없습니다. new(expr)도 이 버전입니다. &x를 만들려고 임시 변수를 두던 직렬화 코드(Age: new(computeAge()))가 깔끔해집니다.
  • 1.27 strings.CutLast, bytes.CutLast, 표준 uuid 패키지, net/url.URL.Clone.
// 1.26
if e, ok := errors.AsType[*NotFoundError](err); ok {
    return http.StatusNotFound, e.Resource
}

// 1.25
var wg sync.WaitGroup
for _, job := range jobs {
    wg.Go(func() { run(job) })
}
wg.Wait()
비판적 시각

log/slog 구조화 로깅

키-값 구조의 로그를 표준으로 제공합니다. Logger(앞단 API)와 Handler(출력 형식과 목적지)를 분리했기 때문에, 라이브러리는 *slog.Logger만 받고 출력 형식은 애플리케이션이 정하는 구조가 가능해졌습니다. 1.26에 slog.NewMultiHandler가 들어와 stdout과 파일, 또는 JSON과 텍스트를 동시에 내보낼 때 직접 핸들러를 쓸 필요가 없어졌습니다.

logger := slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))

    slog.String("order_id", id),
    slog.Duration("took", elapsed),
)

비판적 시각

API가 장황하고 타입 검사가 약합니다. logger.Info("msg", "key", value) 형태는 키와 값이 홀수로 어긋나도 컴파일이 되고, 런타임에 !BADKEY로 찍힙니다. slog.String 같은 타입 생성자를 쓰면 안전하지만 줄이 길어집니다. 성능은 zap, zerolog 대비 할당이 더 많아 초고빈도 로깅에서는 여전히 밀립니다. 결과적으로 "표준이 생겼지만 생태계가 통일되지는 않은" 상태이고, 많은 팀이 slog 인터페이스에 zap 핸들러를 꽂는 절충을 택하고 있습니다.

v1과 다른 기본값이 핵심입니다.

  • 필드 이름 매칭이 대소문자를 구분합니다(v1은 구분하지 않았습니다).
  • 중복 키와 잘못된 UTF-8을 거부합니다.

  • 디코딩이 v1보다 상당히 빠르고, 인코딩은 비슷합니다.
import "encoding/json/v2"

b, err := json.Marshal(v, json.Deterministic(true))
err = json.Unmarshal(b, &v,
    json.MatchCaseInsensitiveNames(true),   // v1 동작이 필요하면 옵션으로
    json.RejectUnknownMembers(true),
)
err = json.MarshalWrite(w, v)              // io.Writer 로 바로

GOMEMLIMIT 소프트 메모리 한도

1.19 지금 도입

그동안 GC 조절 수단은 GOGC(힙이 몇 % 늘면 GC를 돌릴지) 하나였습니다. GOMEMLIMIT은 "전체 메모리를 이 이상 쓰지 말라"는 상한을 주고, 그 근처에서 GC가 더 공격적으로 돌게 합니다. 컨테이너 메모리 제한의 80~90% 정도로 잡는 것이 일반적인 출발점입니다.

GOMEMLIMIT=2750MiB GOGC=off ./server   # 한도만으로 운영하는 극단적 설정
// 또는 코드에서
debug.SetMemoryLimit(2750 << 20)
현업에서

Weaviate는 이 설정 하나로 고메모리 워크로드의 OOM kill이 크게 줄었다고 보고했고, Grafana 계열 도구들은 cgroup 한도를 읽어 자동 설정하는 automemlimit을 기본 탑재했습니다. Kubernetes에서 메모리 limit을 주는 서비스라면 사실상 필수 설정입니다.

비판적 시각

한도에 딱 붙으면 GC가 연속으로 돌면서 CPU를 먹는 "GC 데스 스파이럴"이 올 수 있습니다. 런타임이 GC CPU 사용을 50% 근처로 제한하는 안전장치를 두긴 했지만, 그 상태는 이미 서비스가 느려진 뒤입니다. 한도를 너무 타이트하게 잡지 말고 메트릭(/gc/heap/live:bytes, GC CPU 비율)을 같이 봐야 합니다.

testing/synctest 가짜 시계와 격리 버블

1.24 실험 → 1.25 정식 → 1.27 지금 도입

synctest.Test(t, f) 안에서 만든 고루틴은 하나의 "버블"에 들어가고, 그 안에서 time 패키지는 가짜 시계를 씁니다. 모든 고루틴이 블록되면 시계가 다음 타이머까지 즉시 뛰고, synctest.Wait()는 버블 안 고루틴이 전부 멈출 때까지 기다립니다. 1.27에 synctest.Sleep(Sleep과 Wait의 결합)이 추가됐습니다.

func TestCacheExpiry(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        c := NewCache(10 * time.Minute)
        c.Set("k", "v")
        time.Sleep(11 * time.Minute)   // 실제로는 즉시 진행된다
        synctest.Wait()
        if _, ok := c.Get("k"); ok {
            t.Fatal("expired entry still present")
        }
    })
}
현업에서

재시도 백오프, 캐시 만료, 컨텍스트 타임아웃, 레이트 리미터처럼 "실제 시간을 기다리던" 테스트가 밀리초 단위로 끝나고 플레이키가 사라집니다. VictoriaMetrics는 이 패키지로 플레이키 테스트를 정리한 경험을 공유했습니다. 다만 버블 밖의 시스템(실제 네트워크, 파일)은 가짜 시계를 모르므로, 그 경계에 있는 코드는 인터페이스로 분리해야 합니다.

1.25 → 1.26 실험 → 1.27 정식 권장

플라이트 레코더(1.25). 실행 트레이스를 메모리 링 버퍼에 계속 기록하다가, 문제가 생긴 순간 "직전 몇 초"만 파일로 떨어뜨립니다. 전체 트레이스는 너무 무거워 운영에 켜 둘 수 없었는데, 이제 p99 지연 스파이크의 원인을 사후에 볼 수 있습니다.

fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{MinAge: 5 * time.Second})
fr.Start()
// ... 느린 요청을 감지한 핸들러에서
if latency > threshold {
    f, _ := os.Create("trace.out")
    fr.WriteTo(f)
    f.Close()
}

고루틴 누수 프로파일(1.27 정식). runtime/pprof에 goroutineleak 프로파일이 추가됐고 /debug/pprof/goroutineleak으로도 받을 수 있습니다. "도달할 수 없는 채널이나 뮤텍스를 기다리는 고루틴"을 런타임이 GC 정보를 이용해 찾아냅니다. Uber가 운영 환경용으로 만든 LeakProf의 아이디어가 표준에 들어온 것이며, 구현자도 Uber의 Vlad Saioc입니다.

go tool pprof http://localhost:6060/debug/pprof/goroutineleak
현업에서

지금까지는 goleak(테스트 전용)이나 고루틴 수 메트릭의 추세로 간접 추정했습니다. 이제 운영 중인 프로세스에서 "어느 코드 위치에서 만들어진 고루틴이 새고 있는지"를 바로 봅니다. 장기 실행 서비스의 메모리 우상향을 조사할 때 첫 번째로 뜰 프로파일이 될 것입니다.

비판적 시각

누수 프로파일은 "영원히 블록된 고루틴"만 잡습니다. 채널을 기다리지 않고 무한 루프를 돌거나, 살아 있는 채널에 붙어 있지만 아무도 보내지 않는 경우는 잡히지 않습니다. 플라이트 레코더도 기록 중 오버헤드가 0은 아니므로, 트래픽이 매우 높은 서비스에서는 샘플링 비율을 정해 두어야 합니다.

go fix 모더나이저

1.26 → 1.27 지금 도입

오랫동안 사실상 죽어 있던 go fix가 1.26에서 완전히 다시 만들어졌습니다. go vet과 같은 분석 프레임워크 위에서 "옛 관용구를 새 API로 바꾸는" 수정기(modernizer) 수십 개를 실행합니다. interface{}→any, v := v 제거, 수동 루프→slices.Contains, for i := 0; i < n; i++→for i := range n, sort.Slice→slices.SortFunc 같은 치환이 포함됩니다. 1.27에 atomictypes, embedlit, slicesbackward 등이 추가됐고, 라이브러리 작성자는 //go:fix inline 지시어로 "이 함수는 이렇게 바꿔 쓰세요"를 선언할 수 있습니다.

go fix ./...          # 모듈 전체에 모더나이저 적용 (diff 를 확인하고 커밋)

비판적 시각

1.27에서 fmtappendf 수정기가 "스타일 논쟁"을 이유로 제거된 것처럼, 어떤 치환이 "더 현대적"인지는 취향이 섞입니다. 자동 치환이 가독성을 떨어뜨리는 경우(과도한 이터레이터 체인)도 있으니 diff를 기계적으로 승인하지 않는 것이 좋습니다.

7비판적 시각 종합

개별 항목의 비판을 모아 보면 몇 가지 큰 흐름이 보입니다. 이 흐름을 알고 있으면 "이 기능은 어디까지 믿고 어디서 멈출지"를 판단하기 쉽습니다.

1. 에러 처리 문법은 끝났습니다.

2025년 6월 Go 팀은 try, ? 등 에러 처리 문법 제안을 더 이상 받지 않겠다고 공식 선언했습니다. 이유는 "문제에 대한 공통 이해가 없고, 문제가 있다는 데에도 합의가 없다"는 것입니다. 10년 가까이 설문 1위였던 불만이 "해결하지 않기로 결정"된 셈입니다. if err != nil은 앞으로도 Go의 일부입니다. [ On | No ] syntactic support for error handling

2. "단순함"의 정의가 바뀌고 있습니다.

제네릭, 이터레이터, 제네릭 메서드가 차례로 들어오면서 언어 사양은 분명히 두꺼워졌습니다. Go 팀은 "읽는 쪽의 단순함"을 지킨다고 말하지만, 이터레이터 논쟁이 보여주듯 그 경계는 사람마다 다릅니다. 팀 차원에서 "어디까지 쓴다"는 가이드를 만드는 것이 예전보다 중요해졌습니다.

3. 호환성은 컴파일 기준입니다.

루프 변수, 타이머 채널, 리다이렉트 코드, JSON 엔진 교체, 암호 rand 인자 무시. 모두 "컴파일은 되지만 동작이 다른" 변경이고, go 줄이나 GODEBUG로 단계적으로 적용됩니다. 이 메커니즘은 잘 설계됐지만, 아는 사람만 압니다. 업그레이드 PR에는 GODEBUG 문서의 해당 버전 절을 링크하는 습관이 필요합니다.

4. 실험 기능은 실험입니다.

arena(1.20)는 실험으로 들어온 뒤 정식화가 보류됐고, simd는 1.26부터 실험 상태입니다. 반면 synctest, json/v2, Green Tea는 실험을 거쳐 정식이 됐습니다. GOEXPERIMENT 뒤의 기능을 운영 빌드에 넣는 것은 "Go 팀이 언제든 바꿀 수 있는 API에 의존한다"는 뜻입니다.

5. 표준 라이브러리가 외부 생태계를 흡수하지만 통일하지는 못합니다.

slog는 zap을, ServeMux는 chi를, slices는 lo를, uuid는 google/uuid를 대체하려 했지만 어느 것도 완전히 대체하지 못했습니다. "표준이 있으니 외부 패키지를 걷어내자"는 결정은 기능 표를 실제로 대조한 뒤에 내려야 합니다.

6. 성능 수치는 Go 팀의 워크로드 기준입니다.

PGO 2~14%, Green Tea 10~40%, 소형 할당 30%. 전부 사실이지만 조건부입니다. DoltHub의 Green Tea 사례처럼 "효과 없음"도 정상적인 결과입니다. 런타임 개선은 기대치가 아니라 사후 확인 대상입니다.
